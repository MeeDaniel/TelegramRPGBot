# Правила работы

## Роли и модели

| Роль | Модель | Reasoning effort |
| --- | --- | --- |
| Главный оркестратор | GPT-6 Astra (`gpt-6-astra`) | `high` |
| Субагенты, реализующие изменения | GPT-6.1 (`gpt-6.1-sol`) | `medium` |
| Написание и изменение тестов | GPT-6.1 (`gpt-6.1-sol`) | `high` |
| Промежуточное ревью | GPT-6.1 Sol Light (`gpt-6.1-sol`) | `low` |
| Итоговое ревью всей большой работы | GPT-6.1 Sol High (`gpt-6.1-sol`) | `high` |
| Остальные задачи | GPT-6.1 (`gpt-6.1-sol`) | `medium` |

- Оркестратор разбивает работу, выдаёт задания субагентам, согласует результаты и отвечает за итог. При запуске субагента явно задавай модель и reasoning effort из таблицы.
- Каждое задание должно содержать конкретную цель, контекст, область разрешённых изменений, ограничения, критерии приёмки и требуемые проверки. Указывай ожидаемый результат: изменённые файлы, результаты проверок либо замечания ревью. Не выдавай расплывчатые задания вроде «улучши архитектуру».
- Разделяй реализацию, написание тестов и ревью согласно ролям. Ревьюер проверяет результат без изменения файлов.
- Параллельные задания должны быть независимыми и не менять одни и те же файлы. Если задача смешивает роли, раздели её на конкретные подзадачи.
- Эта инструкция задаёт выбор модели, но сама не переключает модель текущего чата. Если нужная модель недоступна или текущий оркестратор ей не соответствует, сообщи об этом явно; не заявляй, что используешь другую модель, без фактического переключения.

## Git и GitHub

- Выполняй операции с репозиторием через CLI `git`, с GitHub — через CLI `gh`.
- Работай исключительно в этой директории, переключая ветки через `git switch`. Не создавай отдельные Git worktree или дополнительные клоны для выполнения задач.
- Перед изменениями проверяй текущую ветку и `git status`. Сохраняй чужие незакоммиченные изменения и не включай их в свои коммиты без основания.
- Для отдельной большой задачи пользователя создавай отдельную ветку от актуальной `main`. Небольшие доработки допускается выполнять непосредственно в `main`.
- Обычно одному оркестратору соответствует одна рабочая ветка. Для нескольких идейно независимых целей одного оркестратора допускаются отдельные ветки.
- Все агенты используют общую рабочую директорию: ветку переключает оркестратор только после завершения работы субагентов с файлами. Не выполняй одновременно задачи, требующие разных веток.
- Завершай обычные изменения коммитами после проверки результата. Добавляй в индекс только относящиеся к задаче файлы; не коммить секреты, локальные окружения и сгенерированные кеши.
- Для задачи в отдельной ветке после проверок и ревью выполни push и создай PR/MR с целевой веткой `main`; для GitHub используй `gh pr create --base main`. Для небольшой доработки непосредственно в `main` отдельный PR не требуется. Если remote или доступ отсутствует, сохрани локальные коммиты и сообщи, какой шаг недоступен.
- В описании PR/MR кратко укажи проблему, итоговое изменение, выполненные проверки и существенные ограничения. Создание PR/MR не означает автоматическое слияние.

## Сообщения коммитов

- Используй Conventional Commits: `type(scope): краткое описание`, где scope необязателен. Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`.
- Заголовок должен конкретно описывать изменение, желательно укладываться в 72 символа. Избегай общих формулировок вроде «правки» или «улучшения».
- Добавляй короткое тело только когда оно необходимо для объяснения причины, существенного поведения или несовместимости. Пиши кратко, чётко, без воды, сохраняя всю необходимую информацию.
- Исключение: initial commit этого репозитория должен иметь подробное сообщение с составом исходного проекта, правилами работы и результатами доступных проверок. Последующие коммиты следуют обычному краткому формату.
